1. Response summary

This answers AAJOO HOMES HOST LIST PROPERTY — QA + SEO PUBLISH FIX SPEC, section by section and finding by finding, in the order the document raises them. Every ID is carried over unchanged.

We agree with the document's central decision and it is what the platform already does: the Host does not configure the CMS SEO engine. The Host fills in the listing, an Admin approves it, and the system derives the public page — slug, title, description, canonical, robots, Open Graph, schema and sitemap entry — from the listing's own data. The full CMS controls stay where they are, in the Admin SEO screens, for the SEO team.

Four things in section 4 were not true of the code when we checked, including one that made every Host submission report a failure it had not suffered. All four were fixed during this review and are described in section 12.

2. Section 1 — The QA decision: do not block the listing on the full CMS SEO engine

Agreed, and this is the existing design. Phase 2 and Phase 3 of the CMS SEO specification are not on the Host's path and never were. The Host form collects listing data; the SEO page is generated from it.

The table below is the document's own, with what the platform does in each state and how we know.

4. Section 3 — The Host → Admin → SEO workflow

Each of the eleven steps, with what actually happens.

# Actor Required result What happens
1–5 Host Steps 1–5 saved as a Draft 24 modular tables behind five endpoints. Each save is scoped to property_host_id, so a Host cannot save into another Host's draft.
6 System Submit ⇒ Submitted/Review, not publicly indexable POST /listing/submit. The state machine, the seven declarations, the under-construction rule and a readiness score of at least 70 all have to pass. It then sets is_active = 0.
7 Admin Reviews GET /admin/listing/queue and /admin/listing/detail, with the reviewer's checklist persisted per listing.
8 Admin Approve ⇒ Approved POST /admin/listing/review, behind admin authentication.
9 System SEO generation runs writeSeoFor() regenerates slug, path, title, description, keywords, schema and internal links inside the approval transaction, from the listing as it stands at approval — not as it was at submission.
10 System Publication only after successful generation See the note below.
11 Guest / crawler 200 with correct metadata Verified live.

On step 10, honestly. We do not block an approval when metadata generation fails; we make the failure impossible to matter. The resolver's precedence is page_seo (an editor's own words) → property_seo (generated) → derived from the listing row itself. So a page always has a non-empty title, description, canonical and robots directive even if the generator never ran. We chose that over refusing the approval, because the alternative leaves a Host approved-but-not-live over a slug collision, and the gate's purpose — never publishing a page with an empty title — is met either way. Measured: 0 of 8 stored rows have a blank title or description, and 0 contain the string "undefined".

5. Section 4 — The fourteen findings

ID Sev Finding Status What we did / what is true
SEO-01 P0 No deterministic SEO URL after approval Done — one real defect fixed The URL was always generated automatically; no developer has ever created one by hand. But submitListing itself threw: writeSeoFor had been extracted out of it and the response still referred to slug, which no longer existed in that scope. Reading an undeclared name raises a ReferenceError, and it was raised after the database commit — so every successful submission was reported to the Host as a failure while the listing sat correctly in the queue. Fixed, with a regression test. See section 12.
SEO-02 P0 Page could become public before approval Done Publication is is_active = 1, and only the admin review path sets it. Submit sets it to 0. The Host's payload cannot carry it: no listing endpoint reads is_active, is_verify or verification_status from the request body.
SEO-03 P0 Draft/review/rejected could be indexed Done The resolver computes live = is_active = 1 AND is_deleted ≠ 1 and returns noindex when false — and the edge answers 404, not a 200 with an empty shell, because a soft 404 is the failure this finding is really about. Verified live on a draft.
SEO-04 P0 Duplicate slug ⇒ duplicate URLs Done Unique index uq_property_seo_slug at the database, plus a pre-write collision check that disambiguates with the property id. An empty slug is impossible — it falls back to listing-<id>, and an empty URL path would otherwise have collided with the homepage. Measured: 8 rows, 8 distinct slugs.
SEO-05 P0 Name/location change leaves broken old URLs Done — gap found and closed A 301 was written when an Admin changed a slug in the SEO editor, and not when a Host changed one by renaming their own live property — the same event to a search engine and to anyone holding the old link. The recorder moved to a shared module and both paths now use it. Only a listing that was already live gets a redirect; approving a listing for the first time has no old URL to send anyone from.
SEO-06 P0 Meta title/description blank or "undefined" Done A missing name falls back to what the listing is; the resolver falls back to the listing row. Measured across every stored row: 0 blank titles, 0 blank descriptions, 0 occurrences of "undefined".
SEO-07 P0 Canonical could point at a wrong URL Done Self-canonical, absolute HTTPS, and every other address for the same listing is a 301 to it. Verified live: /property?id=29263 → 301 → /property/garg-resorts-karnal-haryana.
SEO-08 P0 Schema may contain fabricated ratings Done aggregateRating is emitted only when approved, active, undeleted reviews exist and the average is above zero. The generator emits no rating keys at all — asserted by a test that fails if aggregateRating, ratingValue, reviewCount or review ever appears in the generated schema.
SEO-09 P1 Images published without useful ALT Done — gap found and closed ALT was generated for the schema.org ImageObject entries and stored per image in image_seo, but the property page's own <img> tags carried alt="" — so a guest using a screen reader heard nothing where the gallery is. The gallery, the tiles, the thumbnail strip and the lightbox now carry ALT built from category · name · place · which photo of how many, capped at 125 characters. The "no photographs" placeholder keeps an empty ALT deliberately: it is decorative and the sentence beside it already says so.
SEO-10 P0 Approved page may not enter the sitemap Done — gap found and closed The sitemap is built on demand and cached in the process for an hour, and nothing in the listing lifecycle purged it. An approved listing could be missing from the sitemap for up to an hour, and — the direction that matters — a suspended one could stay in it for up to an hour, inviting a crawler to a page that now answers 404. Every decision (approve, reject, request changes, suspend) and every edit to a live listing now purges the sitemap and the resolved-page cache.
SEO-11 P0 Sitemap can contain draft/noindex/rejected URLs Done The query filters on is_active = 1 AND is_deleted ≠ 1, then drops anything a page_seo row marks noindex, sitemap_exclude or not-published. Verified live: 6 URLs in the sitemap, 6 approved listings in the database, and they are the same six.
SEO-12 P1 Host edits after approval do not update SEO Done — gap found and closed Only Submit and Approve regenerated. Steps 1–4 write the very fields the page is derived from — the name, the place, the amenities, the price — and touched nothing. A Host who corrected a live listing's name changed the page a guest sees and left the title, description, schema and public URL describing the old one indefinitely. All four steps now refresh a live listing (and leave a draft alone), which also moves the slug, writes the 301 and updates <lastmod>.
SEO-13 P0 Deleted property serves a generic page Done A deleted listing is non-live by the same rule as a draft: sitemap entry gone, page answers 404 with noindex. A redirect is kept only where one genuinely points at a replacement page; the redirect manager flattens chains rather than accumulating them.
SEO-14 P1 No social metadata Done Open Graph and Twitter tags are written at the edge from the listing's own title, description and cover photo. Verified live, including twitter:card = summary_large_image on a property page — the site default is the smaller card, and a property overrides it because it has a real photograph.

10. Section 9 — Dynamic property logic still works

The generator reads only rows the Host actually saved: their views, their amenities, their experiences, their price, their location. Category-specific attributes are not used to write meta copy at all, which is the strongest form of the rule the section asks for — there is no code path by which a Villa's pool text could appear on an Apartment, because no category attribute reaches the copy generator in the first place. What varies per category is the category label in the title and keywords, which comes from the Host's own choice at Step 2.

So: a feature the Host did not select cannot appear, for any of the eleven category flows.

11. Section 10 — Advanced CMS SEO deferred

Agreed, with one clarification worth having in writing: several of the Phase 2 items the document defers are already built and already live in the Admin SEO screens — the templates system (title and description patterns, previewed and applied), bulk SEO operations, the redirect manager, the Image SEO screen and an SEO health report. They are not on the Host's path and do not block this release; they are simply available to the SEO team now rather than later.

Nothing in Phase 3 — Search Console integration, GA4 SEO reporting, Core Web Vitals, backlink or competitor monitoring — is built, and none of it is required for the Host publish flow.

12. What we changed during this review

Four items in section 4 were not true of the code. All four are fixed, deployed and covered by tests.

SEO-01 — Submit reported a failure it had not suffered

writeSeoFor() was factored out of submitListing() some weeks ago. The submit response still reported slug, which after the extraction referred to nothing at all. Reading an undeclared name in JavaScript raises a ReferenceError — and it was raised after the transaction had committed. The listing was submitted correctly; the Host was told it had failed.

This is the kind of defect that hides behind its own symptom: hosts who resubmit make the queue look like it is duplicating, not like the response is lying.

Fixed by destructuring the writer's result. The regression test asserts the declaration exists, and also demonstrates the failure in miniature so the reason survives in the test file.

SEO-05 — A Host's rename left the old URL dead

recordSlugChange — which removes a rule pointing at the page's own new address, flattens any chain that pointed at the old one, writes the 301 and appends to seo_slug_history — lived inside the Admin SEO controller and was reachable only from there. An Admin retyping a slug left a redirect. A Host renaming their live property did not.

Fixed by moving it to utils/seoSlugHistory.js, unchanged, and calling it from the listing lifecycle as well. It fires only when the listing was already live under the old slug, and only after the transaction commits — a redirect written inside a transaction that then rolls back would point at an address the listing never took.

SEO-10 — The sitemap could be an hour out of date

The sitemap is generated on demand and cached in the process for an hour, which is the right shape; nothing in the listing lifecycle invalidated it. Approving a listing left it out of the sitemap for up to an hour, and suspending one left it in for up to an hour — which is the harmful direction, because it points a crawler at a page that now answers 404.

Fixed. Every review decision, and every edit to a live listing, purges the sitemap document and the resolved-page cache immediately.

SEO-12 — A live listing's page could describe the previous version of itself

Steps 1–4 write the fields the SEO page is derived from and regenerated nothing; only Submit and Approve did. Renaming a live property changed what a guest reads and left the title, the description, the structured data and the public URL describing the old listing indefinitely.

Fixed. All four steps refresh a live listing's SEO after they commit. A draft is skipped — it has no public page for anything to be stale against. Because it goes through the same writer, a rename now also moves the slug, writes the 301 and updates the sitemap's <lastmod>.

And one on the page itself — SEO-09

Every photograph on the property page carried alt="". Correct for a decorative image; wrong for these, which are the content. Fixed across the hero, the side tiles, the thumbnail strip and the lightbox.

14. Developer handoff — the required responses

Question Answer
What listing status triggers SEO generation? Submit writes the identity, Approve regenerates it from the listing as it stands at that moment, and — new in this review — any save of steps 1–4 on an already-live listing refreshes it. Publication itself is a separate fact: is_active = 1 AND is_deleted ≠ 1.
Where is the SEO slug stored? property_seo.pse_slug, with pse_url_path beside it, under unique index uq_property_seo_slug. An SEO editor's override lives in page_seo.slug. Resolution precedence is page_seo → property_seo → derived from the listing row.
What API/service generates SEO metadata? utils/listingSeo.js buildSeo() — pure, no database, fully unit-tested — called by writeSeoFor() in controllers/listingStep5.controller.js. The public head is served by GET /seo/resolve?path=… (utils/seoResolve.js) and injected into the shell at the edge by api/seo-render.ts with api/_seoHead.ts.
How is slug uniqueness enforced? A unique database index is the backstop; a pre-write lookup disambiguates a collision by appending the property id. An empty slug falls back to listing-<id>, and an empty URL path falls back to the slug, so a listing can never claim the homepage's address.
How is Draft/Review/Rejected blocked from indexing? The resolver reports live = false, which produces noindex and a 404 status — a soft 404 was treated as a defect in its own right. The sitemap query filters on the same two columns. Submit and every negative decision set is_active = 0.
How is Admin approval enforced server-side? /admin/listing/review sits behind admin authentication. utils/listingLifecycle.js is a real state machine: it refuses to approve a listing that was never submitted, refuses to let a Host clear a suspension by resubmitting, and re-checks the readiness score at approval rather than trusting the one snapshotted at submission.
How is the sitemap updated? /sitemap.xml is an index over three child sitemaps, generated on demand from the database and cached for an hour. As of this review the cache is purged the moment a listing is approved, rejected, suspended or edited while live. <lastmod> comes from page_seo.modified_at, falling back to the property row's own timestamp.
How are old slugs redirected? utils/seoSlugHistory.recordSlugChange writes a 301 into seo_redirects and an entry into seo_slug_history. It removes any rule that would redirect the page away from its own new address, and re-points anything that pointed at the old address so chains never form. Used by both the Admin SEO editor and — new in this review — the Host's own rename.
How is schema generated and validated? Built from the listing's rows into LodgingBusiness, plus BreadcrumbList at the edge. Values are typed, not string-concatenated; the JSON is escaped for <, U+2028 and U+2029 before it enters the <script> block. A test asserts no rating or review key can appear in generated schema.
How are property images assigned ALT text? Generated at upload from the listing's own words and validated by utils/imageSeo.checkAlt, which rejects placeholders such as "image", "photo" and a bare filename rather than merely counting characters. Stored in image_seo.alt_text and editable in the Admin Image SEO screen, which can also list only the images that are missing one. On the page, a generated ALT is always rendered, so a missing stored value never means a silent image. (Current live data: 20 image records, 7 with a stored ALT.)
How are rating/review values prevented from being fabricated? The rating query returns nothing unless approved, active, undeleted reviews exist and the average is above zero, and the generator emits no rating keys at all. Both are covered by tests.
How are sensitive Host fields excluded? They are never selected into a public payload. The wizard's read endpoint is scoped to the owning Host. Identity and ownership documents are stored as Cloudinary authenticated assets and are only ever served through short-lived signed URLs.

## Ready to retest

### #5 · High/Critical — Guest selection changed after editing the search ✅

**Was:** picking 3 Adults, 2 Children, 1 Infant and reopening the editor showed **5 Adults**.

**Why:** the URL carried only `guests`, which is adults + children. 3 + 2 and 5 + 0 are the
same number, so the party could not be read back.

**Retest**
1. Open the search bar → **Who** → set 3 Adults, 2 Children, 1 Infant.
2. Press **Search**.
3. Reopen **Who**.

**Expect:** 3 / 2 / 1, and the summary reads "5 guests, 1 infant". The counts also survive
into the property page you open from the results.

### #7 · High/Critical — Wrong dates and pricing on property details ✅

**Was:** the property page showed different dates from the ones searched, and priced them.

**Why:** search wrote dates as `YYYY-MM-DD`; the property page parsed them as `DD-MM-YYYY`.
`2026-09-05` was read as day 2026, month 9, year 5.

**Retest**
1. Search any stay with check-in **5 September 2026** and check-out **10 September 2026**.
2. Open a result.

**Expect:** the booking panel shows 5 Sept – 10 Sept and **5 nights**.
Direct check: `/property?id=29262&from=2026-09-05&to=2026-09-10` → "₹29,400 · 5 nights".

Dates arriving from an accepted negotiated deal (`DD-MM-YYYY`) still work — both formats
are accepted now.

### #4 · Normal/Minor — No suggestions for partial location names ✅

**Was worse than reported.** Suggestions were not merely missing for partials — they were
missing for **everything**. Place lookup was proxied to OpenStreetMap's Nominatim, which
blocks datacenter IPs, so in production every query returned nothing, `Delhi` included.

**Retest:** type `Delh` in **Where**.
**Expect:** Delhi, West Delhi, South Delhi, New Delhi.

Suggestions now come from our own listings, so every suggestion leads to real stays.

---

### #6 · High/Major — Irrelevant results for Uttarakhand ✅

**Was:** searching Uttarakhand opened with Uttar Pradesh.

**Why:** two causes. Geocoding was dead (above), so the search had no centre and widened its
radius to 3,000 km — the whole country, where UP's seeded listings dominate. And the seeded
coordinates **do not match their own addresses** (see the data note below), so distance alone
could never fix it. Results are now also filtered by place *name* in SQL.

**Retest:** search `Uttarakhand`.
**Expect:** ~100 stays, all showing Uttarakhand addresses. No Uttar Pradesh.

> Addresses in the seed data misspell it "Uttrakhand". That is cosmetic — the state field is
> correct, which is what the filter matches on.

## Data problem worth raising separately

While fixing #6 it became clear the seeded listings carry **coordinates that do not match
their addresses**:

| City | Real | Stored | Out by |
|---|---|---|---|
| Mirzapur | 25.14, 82.56 | 28.58, 79.90 | ~450 km |
| Jhansi | 25.45, 78.57 | 28.81, 79.02 | ~380 km |
| Bijnor | 29.37, 78.13 | 29.22, 79.51 | ~135 km |

29,226 of the 29,230 live listings belong to the seeded import (host 100); four belong to real
hosts. So **any distance-based behaviour on the site is being judged against fabricated
coordinates** — map pins, "near me", distance sorting and the radius filter all inherit it.

The place-name filter works around this for search. Nothing can work around it for the map.
This is the same seed data already flagged for deletion before the sitemap ships.

1 · Architecture & infrastructure

Three codebases, one backend, one database. Every surface — website, Android app, admin console — talks to the same API, so a booking made on the phone appears in the admin console and the host portal instantly, because they are all reading the same rows.

How configuration works

Every credential is environment-first: the API reads Render's environment variables and falls back to safe defaults. GET /health/env reports — without exposing any value — which required variables are set, whether the database the env points at matches the one the app runs on (dbChecks), and whether payments can collect real money (payments.collectsMoney). That endpoint is the pre-launch gate: it turned red honestly during the audit and each item has been driven green by an actual fix, not a suppressed check.

Deployment is push-to-deploy on both hosts: a push to main rebuilds Vercel (web) and Render (API) automatically. Database schema changes ship as idempotent Sequelize migrations — re-running any migration is a no-op — via a CLI bridge that guarantees migrations run against the same database the app uses.

2 · Roles & account model

One account can be both a guest and a host; the platform keeps the two lives separate through the session, not through duplicate accounts.

  • Guest (renter) — browses, negotiates, books, pays, reviews. KYC is required only at the moment of booking, never for browsing.
  • Host — lists properties, receives offers and bookings, gets paid. KYC happens at signup, so listing is unobstructed afterwards.
  • Admin — a separate login (/admin/login) with its own token, role-based access control on the API (requireRole middleware), and its own session storage so an admin logout can never leak into a guest session on the same browser.

Technically

Login mints a JWT carrying userId, email, isHost and a derived role claim. Host-mode ↔ guest-mode switching calls /user/switch-mode, which mints a fresh token server-side — the app deliberately does not store the password to re-login silently. Unverified accounts can attempt login: the server answers with needsVerification and re-sends a code without issuing a token, and checks the password first so the endpoint cannot be used to probe which emails exist. Google sign-in on both platforms flows through Firebase Auth: the client obtains an ID token, posts it to /user/auth/google, and the backend verifies it with Firebase Admin credentials — account creation gates run before any welcome email is sent.

3 · Platform conventions

Rules that hold everywhere, adopted during the audit because their violations kept producing the same class of bug.

  • Empty means hidden, never zero. A stay with no reviews shows "New", not 0.0 ★. A listing with no photo shows an honest "Photo coming soon" frame, never a stock image of somewhere else. A rail with no inventory (e.g. Kufri) hides itself.
  • No invented numbers. "1,240 verified homes", "18 new this week", "3× more views" — all removed. If nothing measures it, the UI does not claim it.
  • Paid placement is disclosed. Anything ranked because money changed hands carries a visible "Sponsored" label distinct from the Verified badge.
  • Server decides money. Clients send flags and intents (useWallet, a coupon code); amounts are always computed server-side from state the server holds. Checkout modals take their amount from the server's payment order, never from a locally computed figure.
  • Guards fail open, payments fail closed. A hiccup in a safety check (booking-overlap lookup, boost ranking, wallet balance display) degrades to the permissive behaviour and logs; anything that moves money requires positive verification (HMAC signatures) to proceed.
  • Idempotency by unique reference. Wallet entries, referral rewards and refunds carry unique reference keys (REF-, BOOK-, BOOKREFUND-) so any retried or double-fired operation collides and becomes a no-op.
  • Dates travel as DD-MM-YYYY between clients and API for bookings.
  • Web ↔ app parity. A fix on one platform lands on the other in the same pass (standing rule since 9 Aug), with a shared ledger of gaps.

4 · Discovery — explore, search, maps

The front door Web

The bare domain resolves to Explore for visitors, and straight to the right dashboard for signed-in users (host → host dashboard, guest → account dashboard), decided by reading the role from the session token. Explore shows destination tiles with real inventory counts (a state-grouped query with a 5-minute cache; only places with ≥10 listings appear), property rails, and search.

Search Web App

Non-technical: type a place, get stays around it, filter by category, see them as cards and on a map. Boosted stays appear first with a Sponsored label.

Technical: one endpoint serves every guest surface — POST /properties/search takes latitude/longitude/radius/category and runs a two-pass query: pass one resolves the nearest N ids by Haversine distance in SQL (capped, so a wide search cannot return the entire 29k catalogue — that once produced a 23.6 MB response); pass two loads those ids with their relations, fetched as separate queries rather than joins to avoid the cartesian-product blow-up (measured: 997ms joined vs 745ms separate). Images, ratings and host-visibility are then attached in one Promise.all. Active boosts elevate to the top (tier ladder), each row carries isBoosted, and listings from deactivated hosts are filtered out.

The map App

The app's home is a map (Google Maps) with custom ₹ price-bubble markers drawn on a canvas, a draggable bottom sheet carrying the result list, category pills, and the LUX toggle. Three behaviours worth knowing:

  • Pan-to-search — sliding the map to a new area re-queries around the camera centre once it settles more than 1.5 km from the last search (the threshold is also what stops the re-centre animation from re-triggering itself).
  • Re-centre button — takes a fresh GPS fix and re-syncs both camera and search to it.
  • Honest fallbacks — if location is declined, properties still load around the last known position (the map never opens empty over California, which the emulator default once caused).

LUX mode App Web

A switch into the luxury catalogue (is_luxury listings) with its own visual identity in the app: near-black + gold palette, its own loader, filled icons, slower motion. The switch dialog is themed for the direction of travel and holds the LUX loader until luxury listings have actually landed.

Pre-booking App Web

Advance booking of stays by area — rails for Shimla, Kufri, Mohali, Panchkula, Kharar and Chandigarh (12 stays each, matched on address because city labels in the imported catalogue are unreliable), check-in/check-out pickers that carry into the property page, and a 10% advance payment model. Known limitation the backend has no first-class "deposit" concept yet — the advance is charged as the booking price, which is recorded honestly in the tracker as needing a proper advanceAmount model.

5 · The property page

The same seven-panel structure on web and app, rendered from one shared implementation on the app side so the two screens cannot drift.

  • Gallery — swipeable photos with counter; no photos means no gallery, never stock.
  • Tabs — About · Amenities · House Rules · Location (map) · Guest experiences (reviews) · Host · Policies. Real tab panels on both platforms.
  • Verified badge — driven by the listing's real verification status, not the legacy always-on flag.
  • Nearby — distances to airport / hospital / park / bus stand etc., from property_nearby_places (host wizard writes it; admin can edit it). Sub-kilometre distances render in metres. Absent data renders nothing — never "0 km to the airport".
  • Ratings — a real average and count from reviews, or "New". (Both platforms previously invented 4.5/4.6 defaults; those are gone.)
  • Sticky price bar — per-night rate, total for chosen dates, and the two calls to action: Book now and Negotiate.

Technical: detail loads from GET /properties/:id plus separate calls for reviews, nearby groups and availability. Booked date ranges come from POST /booking/property-availability and grey out taken nights in the date picker on both platforms.

6 · Negotiation — the platform's signature

Non-technical: a guest offers a price for their dates; the host accepts, declines or counters in a chat; an accepted price becomes a personal 24-hour coupon that books the stay at exactly the agreed amount.

Technical: offers live in a thread keyed on property + the two parties, with a server-maintained offer_number sequence. The receiver is always resolved from the property's own host — never trusted from the client. Chat is Socket.io with a REST fallback; the accept path mints a one-time coupon whose discount percentage is ceiled so rounding can never bill the guest above the agreed price (a real ₹1 overcharge found and fixed in audit phase 7). Hosts see offers in a dedicated screen ("Awaiting you" first) and in the Messages tab — guest conversations are the negotiation threads, so there is no second messaging system to drift. Admins can read all negotiation messages (/admin/negotiations/messages).

7 · Booking & payment

Non-technical: pick dates, see the price with GST, choose Pay online / Pay at property, optionally apply wallet credit, pay, get a confirmation screen, an email (both sides), a WhatsApp message, and an invoice.

The guards, precisely

  • Double-booking: a booking is refused if its dates overlap any live reservation on the property — including online checkouts still pending payment, held for 30 minutes so two guests cannot pay for the same nights, but never longer, so an abandoned checkout cannot lock dates.
  • Pay-on-arrival: one active POA booking per guest, enforced server-side (the app's display logic agrees with it, keyed on status ids, not titles).
  • Both guards fail open: an unexpected error in the check logs and lets the booking proceed rather than blocking legitimate guests.

Pricing & tax

Clients send the pre-tax room subtotal; the server computes GST — 5% for stays at ₹7,500/night or below, 18% above — and stores subtotal, tax, rate and total on the booking. (The app once sent the taxed total and got taxed twice; that class of bug is why the server owns the math.) Booking ids are human-readable (B454535) with a matching invoice number.

Confirmation

A real confirmed route (not a dialog that can miss), showing dates, amounts, paid vs due, and an in-app map with Get Directions. Emails go to both guest and host on every paid booking (they once fired only for pay-on-arrival), WhatsApp confirmation goes via BotPenguin, and in-app bells notify host and admin.

8 · Referral & wallet

Non-technical: share your code; when a friend signs up with it, ₹300 lands in your wallet immediately. Wallet money pays for stays — fully, or as a part-payment where the gateway charges only the difference. The invoice names both methods.

Technical: the wallet is an append-only ledger (tbl_wallet_transactions) — balance is always the sum of credits minus debits, never a mutable column that can drift from its own history. Unique references make every credit/debit replay-safe. Debits ride inside the booking's database transaction after a row-locking balance read, so two simultaneous checkouts by one guest serialise and a rupee cannot be spent twice; if the booking rolls back, the debit rolls back with it. Cancellations refund the way the guest paid: wallet portion back to the wallet instantly, only the gateway-captured remainder through Razorpay. Referral codes are deterministic (AJ + base36 of the user id) — flagged: pay-at-signup plus guessable codes is farmable, and one of three small anti-abuse rules should be picked before real-money launch.

11 · Listing a property

Two generations coexist, by design:

  • Legacy form (live on both platforms): the app's 6-step wizard (Type / Location / Photos / Pricing / Preferences / Publish) posting once to POST /properties/add; the web's equivalent form. New listings land as Pending and appear publicly only after admin verification.
  • Listing Engine (live on web at /redesign/host/list-property): a schema-driven 5-step wizard — the client fetches GET /listing/schema (29 top-level groups, per-category flows, conditional visibility rules) and walks /listing/step1..step5 with draft resume, a media pipeline (upload/patch/delete), a readiness check and a final submit, writing ~24 modular tables (foundation, location, capacity, amenities, house rules, cancellation tiers, nearby places, compliance, contacts…). Porting the app onto this engine is the one large open feature — blocked on a design the sheet references but never shared.

12 · Boost — paid placement

Non-technical: a host pays ₹499/week, ₹1,499/month or ₹3,999/quarter to put a listing at the top of guest searches, wearing a "Sponsored" label. Higher tiers outrank lower ones. The plan copy promises exactly what ships — placement, ladder, badge, duration — and nothing else.

Technical: purchase is order → Razorpay checkout → HMAC verify (the same signature machinery as bookings). The paid window is stamped at verification, so an abandoned checkout doesn't consume paid days; one live boost per property; a re-fired verify is idempotent; a forged signature is refused without burning the pending order (a bug found by adversarially testing the endpoint before trusting it). Ranking: active boosts elevate in the guest search with the tier ladder (pro > growth > starter), stable within groups so nearest-first survives; expiry is time-bounded in the query itself so a boost stops ranking the second it ends. The admin's property table is deliberately not ad-ranked. Revenue lands in the financial ledger as BOOST_PAYMENT. Verified live: a boosted listing outranked a physically nearer one on web and app, with the chip rendered on both.

13 · The money path

Audited end-to-end in phase 6 and found arithmetically exact. Every rupee that moves writes ledger rows; every paid booking gets an invoice; every host credit queues a payout.

What one paid booking produces

ArtifactContent
Ledger rows (tbl_financial_ledger)GUEST_PAYMENT (credit, full amount) · HOST_EARNING (host's share) · PLATFORM_COMMISSION (15% of subtotal) · commission GST (18% on the commission) · TAX_COLLECTED (the stay's GST). Pay-on-arrival records as PENDING — visible but not counted as revenue until collected. Other types: REFUND, PAYOUT, ADJUSTMENT, BOOST_PAYMENT.

Payout rowHost's net queued for disbursement (§14).

Tax rules: stay GST is 5% at ≤ ₹7,500/night, 18% above; platform commission is 15% with 18% GST on the commission itself. All splits are computed once, server-side, in financeRecorder.

14 · Host payouts

Admin sees a full payout detail view — host, booking, guest, masked bank details — and every finance export opens with the report name, period covered and generation time so a saved file can never be mistaken for a different filter's output.

15 · Cancellation & refunds

Non-technical: cancelling computes what the guest is owed from the property's cancellation policy and how far ahead of check-in they are, tells them the exact amount and method, and sends the money back the way it came.

Technical: policies are per-property (including a Custom policy with its own hours-before → refund-% ladder stored per listing). The cancellation itself commits first — status, refund fields, history row, in one transaction — and money moves after, so a gateway hiccup can never leave a booking in limbo; failures are recorded for manual settlement rather than thrown at the guest. Refunds are wallet-first for wallet-paid portions, then Razorpay for the captured remainder. The host's queued payout is withdrawn on a full refund and put on hold with the reason recorded on a partial one. Both sides receive a cancellation notice that states the money outcome explicitly — including "nothing was charged" for unpaid bookings.

16 · Identity verification (KYC)

The policy: hosts verify at signup (so listing is frictionless afterwards); renters browse freely and verify at their first booking. Decided 13 Aug and live on both platforms.

Technical: DIDIT drives verification with two separate workflows (guest / host). createSession applies a 90-day skip for already-verified users so a verified renter isn't re-asked at every checkout; a force flag exists for deliberate re-verification (Profile → Update documents), because the skip once made re-verification impossible while blaming an outage. Decisions arrive by webhook and are recorded on the account; each booking snapshots the guest's verification status at booking time. On Android, DIDIT opens in the system browser and the OS may kill the app meanwhile — so the in-progress booking is saved to disk first, and a "Finish your booking" banner restores property + dates on return. The "Verified" chip reads the DIDIT decision — uploading a document is not verifying.

20 · Ops, environments, test accounts

Environments & deploys

  • Web: push to main → Vercel build → www.aajoohomes.com.

  • App: flutter build apk; Play Store release pending (needs the production API host decision — the shipped app currently points at the dev backend URL — plus a release keystore and Firebase SHA-1 registration).
